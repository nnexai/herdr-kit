# Where the coordinator could run

Research, 2026-11-16. No implementation or deployment is proposed for immediate execution. **Recommendation: keep one authoritative coordinator and journal; let other machines be execution hosts, not competing coordinators.** Start on the desktop; move the authority to an always-on home host only if availability warrants it. For shared live state, prefer a small private API over synchronizing writable files.

Current behavior below is observed; proposed architectures, tradeoffs and staging are [INFERENCE], not tested support.

## Today: portable records, machine-bound execution

Observed in the current source and installed tools:

- `<data-dir>/coord/` owns monthly append-only `journal/*.jsonl`, derived `state.json`, briefs, results, roles, configuration, OMP sessions and the coordinator's home. The fold holds workstreams, tasks, resource ownership, decisions, questions, instructions, session references and **one inbox cursor**. Roles/configuration and result/transcript contents are separate files, not recoverable from the journal alone. See [storage paths](../../crates/kit-coord/src/coord/paths.rs#L26), [state](../../crates/kit-coord/src/coord/state.rs#L14) and [spec](../coordinator-spec.md#3-storage).
- CLI processes, delegates and the watcher can all append, but share one exclusive `flock`: under that lock they read state, assign `last_seq + 1`, append/fsync and update the fold cache. This is **one serialized writer stream**, not one writer process. The fold rejects duplicate/out-of-order sequence numbers; it is not a journal merger. [Journal](../../crates/kit-coord/src/coord/journal.rs#L118), [fold](../../crates/kit-coord/src/coord/fold.rs#L52).
- Launch uses `hc run`, labels and an absolute working directory; `herdr-app ls/do` supplies tab discovery and naming. Observation follows `hc events` and reconciles terminals, spaces and Git worktrees. Reports validate a local result file and journal its absolute path, not its contents. Cleanup checks ownership, process identity, recorded sessions/results, worktree dirtiness and commit reachability. These operations depend on the right machine's filesystem and runtime. [Launch](../../crates/kit-coord/src/coord/launch.rs#L53), [report](../../crates/kit-coord/src/coord/place.rs#L1100), [watcher](../../crates/kit-coord/src/coord/watch.rs#L462), [release](../../crates/kit-coord/src/coord/release.rs#L55).
- The native Coordinator dialog executes a binary against a local data root and watches the journal; it also reads the coordinator's local OMP transcript through the CLI. Copying `state.json` would not produce a functioning remote client. [Status store](../../mods/kit-coord/store.js), [dialog store](../../mods/kit-coord-ui/store.js), [conversation](../../crates/kit-coord/src/coord/conversation.rs#L123).

**Important qualification: Herdr already supports remote machines.** Installed `hc 0.1.21` documents `run --on MACHINE`, `machine/t7` addresses and SSH machine connections; the installed app guide describes remote spaces. Upstream says the local core aggregates remote lists/events while the destination owns programs and files. However, kit-coord's [launch adapter](../../crates/kit-coord/src/coord/adapter.rs#L192) passes no `--on`, its state has no explicit host identity, and its file/Git/session operations remain local. Reuse Herdr's transport rather than assume a new remote terminal daemon is necessary. [Herdr machines](https://github.com/herdrdev/herdr-core/blob/master/docs/machines.md), [app model](https://github.com/herdrdev/herdr-app/blob/master/defaults/AGENTS.md#the-model-spaces-tabs-terminals).

Core sockets are machine-local Unix endpoints, not shared-data interfaces; SSH carries the remote protocol. Terminals/PIDs, OMP sessions and authentication, repo/worktree paths, app control endpoints and installed executable paths therefore pin today's coordinator to its host. Herdr's remote transport does not make those paths portable. [Core security](https://github.com/herdrdev/herdr-core/blob/master/docs/security.md).

## Where it could live — assessment

| Location | Advantages | Costs and constraints |
|---|---|---|
| Local desktop, today | Lowest interaction latency; repos, credentials, GUI and tools already present. No new service to administer. | Work stops when the machine sleeps or loses power; being away is fine only while it stays awake and connected. Telegram delivery also depends on this host or a separate bridge staying online. |
| Always-on home server / VM | Available while laptops sleep; low LAN latency; private storage under the person's control. Good long-term home for one authority. | Needs repo clones, toolchains and its own credentials. Home power/internet remain failure points; a VM on a sleeping desktop solves nothing. Current kit-coord needs app operations: a headless core alone is not a proven drop-in replacement. |
| Remote host over Tailscale / SSH | Independent of home/desktop power; suitable for unattended work and outbound Telegram. | WAN latency, hosting cost, credential exposure and data-residency tradeoffs. Local-only hardware/files stay on worker machines. The same kit-coord app/control dependency must be resolved. |

Herdr core keeps programs alive without an open window, but kit-coord currently calls the app for placement/reconciliation/cleanup. A server needs either a supported app/control environment or a deliberate separation of those duties; neither was tested here. Keep coordinator/watcher visibility from the person's desktop rather than introduce hidden agents.

[Tailscale SSH](https://tailscale.com/kb/1193/tailscale-ssh) provides private authenticated access, not orchestration or data consistency. Direct connections are generally faster than relays; actual WAN/relay latency is unmeasured. [Connection types](https://tailscale.com/kb/1257/connection-types). Telegram is a separate integration, not a built-in transport in the reviewed coordinator code: outbound HTTPS notifications and long-polling replies can work from any online host without public inbound access. Use one authorized bridge, keep its token private, and do not equate an awake coordinator with an awake desktop worker. [Telegram API](https://core.telegram.org/bots/api#getting-updates).

## Multi-machine models — proposed options

**(a) One central coordinator, several execution hosts — preferred.** The authority places a task on a named host. Reuse `hc run --on` and machine-qualified terminal addresses for launch/observation; add host-aware repo, session and resource records. Execute worktree creation/checks/deletion on the owning host, using its local core and the appropriate app/control route. Transfer briefs and completed results explicitly; a remote reporter submits only its own task's events to the authority. On disconnect, mark observations unavailable, not resources gone; reconnect/reconcile before any cleanup. The central coordinator remains a single availability dependency, but already-running workers can continue and retain reports until acknowledged.

**(b) A coordinator per machine, sharing one journal/state — reject active-active.** Each would launch, watch and clean locally, but the present fold has one coordinator, watcher and cursor. Two decision makers can duplicate tasks or acknowledge each other's work even with perfectly serialized appends. Making this safe requires leader election/fencing, host-scoped observation and redesigned ownership/cursors; if only one leader acts, it effectively becomes (a) with standby processes. Replicating files does not solve decision ownership.

**(c) Federation or explicit handoff — useful only for a different need.** Federation gives each machine its own journal/coordinator: local launch/watch/cleanup remain local, with summaries/results exchanged and cross-host tasks explicitly assigned to one owner. It tolerates independent offline work but sacrifices one simple authoritative conversation. Handoff instead moves one authority: quiesce/fence the old owner, transfer a consistent journal plus files/configuration, then start a fresh coordinator on the new host. Existing delegates remain on their original hosts and are reconnected, not copied. An unreachable old owner cannot safely be assumed dead. Today's `handoff` refreshes a session on the same installation; it is not machine migration.

## Sharing the journal and results — assessment

| Option | Fit and failure mode |
|---|---|
| Syncthing / shared filesystem | Syncthing copies files asynchronously and creates conflict copies; it does not share kernel locks or merge JSONL events. Two hosts can both issue sequence N; conflict files are not read as monthly journals. Useful for one-way exports/backups of finalized artifacts, not a live writable coord tree. [Syncthing](https://docs.syncthing.net/users/syncing.html). NFS is different: modern Linux can propagate `flock`, but mount options, lock recovery, caching, fsync/rename semantics and partitions must all be correct. `O_APPEND` alone is unsafe for concurrent NFS appenders. Even correct locking leaves the multi-coordinator ownership problem. [flock](https://man7.org/linux/man-pages/man2/flock.2.html), [open](https://man7.org/linux/man-pages/man2/open.2.html). |
| Git-backed journal | Good private audit snapshots and committed results; poor live inbox. Concurrent append histories need semantic reconciliation, not a text merge. Push rejection can serialize publication, but cannot undo a delegate launched before its push won. Authorize actions only after authoritative acceptance and this becomes a command service built around Git. [Git push](https://git-scm.com/docs/git-push). Never put private operational records in the public project repo. |
| Small owner API over Tailscale | Best live-sharing boundary: one host validates commands, serializes journal writes/fold, serves board/inbox/history and stores uploaded results. Clients submit commands, not arbitrary trusted journal events. Keep existing local JSONL initially; SQLite is optional, not a prerequisite. Requires explicit authorization, reconnect behavior and service operation. |
| SQLite + Litestream | SQLite on the authority gives transactions and conditional updates; Litestream adds asynchronous disaster-recovery replication, not multi-writer coordination or automatic safe failover. It also does not back up external result/session files unless separately arranged. Keep SQLite local behind a server, not directly opened across NFS. [Litestream](https://litestream.io/how-it-works/), [SQLite network guidance](https://www.sqlite.org/useovernet.html). |
| CRDT / event sync | Supports offline concurrent data changes, but convergent records do not prevent two launches, conflicting answers or unsafe deletion. Would need globally unique events, causal ordering, new fold semantics and exclusive action ownership. Attractive for shared notes, disproportionate for this control plane. [Automerge](https://automerge.org/docs/hello/). |

The consistency contract is the key: one authority assigns sequence numbers and folds accepted transitions. Today locks and identity/state rechecks provide local conditional behavior; there is no general distributed CAS API. Remote commands need **compare-and-swap (CAS)** against expected task/resource/session versions, plus stable request IDs so a lost reply does not duplicate an action. Owner changes need fencing, not just a heartbeat timeout. Persist launch intent before acting, reconcile uncertain outcomes, and store/acknowledge result contents before recording an available result reference. Network outages must not trigger speculative cleanup or a second coordinator.

Keep repositories as per-host clones and local worktrees; exchange commits through the normal Git remote, not a synced live `.git` or worktree directory. Map logical repo identity to host-specific paths and use host-qualified runtime IDs. Keep secrets, keyrings, SSH private keys and OMP credentials per machine, granting only what each host needs. Session transcripts may contain secrets; retain them on their host by default and back up selectively/encrypted. Do not synchronize the whole data root, sockets, locks, heartbeat, binaries or app state.

## Simplest path and decisions for the person

1. **First, distinguish access from execution:** one desktop coordinator plus private remote access/backups may already satisfy “use it while away.” No shared writable state is needed.
2. **If unattended availability matters, choose one stable home host.** Resolve the app/control and visible-client requirements before moving anything; transfer authority explicitly, not through two-way sync.
3. **Only when work must execute on several hosts, add (a):** reuse Herdr remote terminals; add host-local resource operations and authenticated reporting/result transfer to one owner API. Keep JSONL until an actual storage need justifies SQLite. Add disaster-recovery backups, not active-active failover.

Open questions: Must it keep working when the desktop is off, or merely be reachable remotely? Which work needs a particular machine/hardware/OS? Must machines coordinate while disconnected, or can scheduling wait? Is a home host sufficiently reliable, or is paid remote hosting acceptable? Should the person use native Herdr, Telegram, or both while away—and is status/answering enough, or is full terminal access needed? What credentials/transcripts may leave each machine, and how much recovery-time/data-loss risk is acceptable?

Verification was read-only: repository/history inspection, installed CLI help and coordinator status. No remote launch, partition, migration, Telegram delivery or headless-server scenario was exercised; those capabilities are proposals, not verified support.
